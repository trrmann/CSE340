app.use((err, req, res, _next) => {
  console.error('Error occurred:', err.message);
  console.error('Stack trace::', err.stack);
  const status = err.status || 500;
  const template = status === 404 ? '404' : '500';
  const context = {

    error: err.message,
    stack: err.stack,
  };
  res.status(status).render(`errors/${template}`, context);
});

When a controller calls next(err), Express skips every remaining normal route and middleware and jumps straight to this handler, because it's the one registered with four parameters.

ASSISTANT:
That's a great question, Tracy, and yes, a server class is a natural next step for your design. Here are the improvements I'd recommend, roughly in order of value:

1. A Server (or App) class. Today server.js builds the app, registers middleware, the router, the 404 catch-all, and the error handler, and starts listening, all at the top level. A class could split that into clear methods, such as configureMiddleware(), configureRoutes(), configureErrorHandling(), and start(port) / stop(). The biggest benefit is testability: a test could create the server on a spare port, run requests against it, and stop it, instead of launching a separate process. The order you just explained (routes, then 404, then error handler) would also be enforced in one place. Keep server.js as the small entry point that creates the class and calls start(), so the file the course expects is still there.

2. A small HttpError class (for example, new HttpError(404, 'Category Not Found')). Right now each controller builds a 404 in three lines (new Error, set err.status, next(err)). One class removes that repetition and makes every error carry a status from the start.

3. A base controller class. Your controllers repeat the same "convert req.params.id with Number(), check it's a positive integer, otherwise 404" logic. A shared parent class (or a helper method) such as parseId(req) keeps that rule identical everywhere, the same way PgDBConnection already centralizes your database rules.

4. Passing models into controllers (dependency injection). Each controller creates its own models with static fields. Accepting them through the constructor instead, such as new CategoriesController({ categoriesModel, projectsModel }), would let tests pass in fake models that don't need a database.

One caution for grading: the rubric checks that files and function names follow the course patterns, so keep the same files, routes, and function names, and add these as structure underneath, as you did with your model aliases.
